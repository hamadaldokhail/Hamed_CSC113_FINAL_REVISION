Objects & Methods — the foundation

A class is a blueprint that defines attributes (fields) and behaviour (methods). An object is a live instance of that class created with new.

Class structure

public class Car { // ─── Fields (attributes) ─── private String brand; // instance field private int speed; private static int count = 0; // static field — shared by ALL objects // ─── No-arg constructor ─── public Car() { brand = "Unknown"; speed = 0; count++; } // ─── Parameterised constructor ─── public Car(String brand, int speed) { this.brand = brand; // this.brand = instance field; brand = parameter this.speed = speed; count++; } // ─── Constructor chaining with this(...) ─── public Car(String brand) { this(brand, 0); // MUST be first line — calls the 2-param constructor } // ─── Instance methods ─── public String getBrand() { return brand; } // ─── Static method ─── public static int getCount() { return count; } // ─── Method overloading ─── public String info() { return brand; } public String info(String prefix) { return prefix + brand; } }

The this keyword — 3 uses

Use 1

Refer to instance field

this.name = name; // distinguishes field from param
Use 2

Call another constructor

Use 3

Shape s = this; // pass self as argument

Static vs instance — know the difference

Instance member
  • One copy per object
  • Access: object.field
  • Can use this
  • Example: car.brand
Static member
  • One copy shared by all
  • Access: ClassName.field
  • Cannot use this
  • Example: Car.count
🚫 Trap — static method accessing instance member:
A static method cannot directly call instance methods or access instance fields. You must create an object first.
public static void main(...) { brand = "X"; } → ❌ compile error
public static void main(...) { Car c = new Car(); c.brand = "X"; } → ✅

Method overloading

// Same name, different parameter list — resolved at COMPILE TIME public void print() { ... } public void print(String s) { ... } public void print(int x, int y) { ... } // DOES NOT count as overloading — return type alone doesn't distinguish! public int getValue() { ... } public void getValue() { ... } // ← COMPILE ERROR

Exam traps & key rules

🚫 Trap 1 — default constructor disappears:
If you define ANY constructor, Java no longer provides the default no-arg constructor. If other code calls new MyClass() and you only wrote MyClass(int x) → compile error.
🚫 Trap 2 — this(...) must be first:
Constructor chaining with this(...) must be the very first statement. Same for super(...). You cannot have both in the same constructor.
🚫 Trap 3 — name = name does nothing:
Inside a constructor, name = name assigns the local parameter back to itself. Always use this.name = name to set the instance field.
💡 Exam tip — tracing constructors:
When asked for output, trace EVERY constructor call in order. Watch for this(...) chains — execution jumps to the other constructor and runs it completely before returning.

Inheritance — IS-A relationship

A subclass inherits non-private members from its superclass and can override methods to provide specialised behaviour. Keyword: extends.

Syntax & constructor chaining

public class Shape { protected String name; protected String color; public Shape() { name = "I am a Shape"; color = "White"; System.out.println(name + " -- " + color); } public Shape(String a, String b) { name = a; color = b; System.out.println(name + " -- " + color); } } public class Rectangle extends Shape { private String name; // ← HIDES Shape.name (separate field!) private double length, width; public Rectangle() { // no super() → Java inserts super() automatically name = "I am a Rectangle"; color = "Blue"; // color comes from Shape (protected) length = 2.0; width = 1.0; System.out.println(name + " -- " + color + " -- " + length + " -- " + width); } public Rectangle(double l, double w) { this("I am Rectangle", "Green", l, w); // chains to 4-param constructor } public Rectangle(String a, String b, double l, double w) { super(a, b); // calls Shape(String, String) name = a; color = b; length = l; width = w; System.out.println(name + " -- " + color + " -- " + length + " -- " + width); } }

Constructor call order — new Rectangle() traced

Execution order for new Rectangle()
1. Rectangle() no-arg is called
2. No super() written → Java auto-inserts super() → Shape() no-arg runs
3. PRINT: "I am a Shape -- White"  ← Shape() output
4. Control returns to Rectangle() — continues execution
5. PRINT: "I am a Rectangle -- Blue -- 2.0 -- 1.0"  ← Rectangle() output

Hidden fields — the biggest midterm trap

public class Shape { protected String name = "Shape"; } public class Rectangle extends Shape { private String name = "Rectangle"; // new field — HIDES Shape.name } // Inside Rectangle methods: // this.name → "Rectangle" (Rectangle's own field) // super.to_String() → uses Shape's 'name' field → "Shape" // Shape s = rectangle_object; // s.name → "Shape" (reference type = Shape, field binding is static) // s.to_String() → Rectangle's version (method = dynamic dispatch)
🚫 Critical — hidden fields vs overridden methods:
Fields are HIDDEN — each class keeps its own copy. s.name where s is of type Shape always gives Shape's name, even if the actual object is a Rectangle.
Methods are OVERRIDDEN — only one version exists at runtime, always the most derived one.
This asymmetry is the KEY to solving Q1 of the midterm.

Method overriding rules

  • Same method name, same parameter list, same (or covariant) return type
  • Cannot make access more restrictive: if parent's method is public, override must also be public
  • Use super.method() inside the override to call the parent's version
  • @Override annotation is optional but recommended — causes a compile error if the signature doesn't actually match
public String to_String() { String s = super.to_String(); // calls Shape.to_String() — uses Shape's fields s += "\n <L = " + length + ", W = " + width + ">"; return s; }

Exam traps

🚫 Trap 1 — missing no-arg parent constructor:
If the parent class has a parameterised constructor but no no-arg constructor, and the subclass constructor doesn't call super(args) explicitly, Java tries to insert super() → compile error because no-arg Shape() doesn't exist.
🚫 Trap 2 — super() must be first:
Just like this(...), super(...) must be the absolute first statement in any subclass constructor. No code can run before it.
💡 Tracing tip:
When tracing inheritance output, always follow the constructor chain from the top. Draw a stack: each constructor call pushes, each return pops. Print statements happen in the order the code executes top-to-bottom within each constructor.

Polymorphism — same call, different behaviour

The ability of a method call to behave differently based on the actual runtime object type. There are two kinds: runtime polymorphism (method overriding) and compile-time polymorphism (method overloading).

The golden rule — THE most important concept

Fields → reference type (static)

Field access is decided at compile time based on the declared type of the variable — NOT what object it actually holds.

Shape s = new Rectangle(); s.name // → Shape's name field
Methods → actual object type (dynamic)

Method calls are resolved at runtime based on the actual object stored in the variable.

Shape s = new Rectangle(); s.to_String() // → Rectangle's version

Direct midterm Q1 trace — display() method

public void display() { System.out.println(name + " -- " + to_String()); // ↑ Rectangle's name ↑ Rectangle's to_String() (called on this = Rectangle) Shape s = this; System.out.println(s.name + " -- " + s.to_String()); // ↑ Shape's name ↑ Still Rectangle's to_String()! } // s is declared as Shape → field s.name uses Shape's name (static binding) // But the actual object is Rectangle → s.to_String() calls Rectangle's override (dynamic)
Output of display() when called on new Rectangle()
Line 1: "I am a Rectangle -- [I am a Shape -- Blue]<newline> <L = 2.0, W = 1.0>"
→ name = Rectangle's own name = "I am a Rectangle"
→ to_String() = Rectangle's version → calls super.to_String() (uses Shape.name="I am a Shape", Shape.color="Blue")
Line 2: "I am a Shape -- [I am a Shape -- Blue]<newline> <L = 2.0, W = 1.0>"
→ s.name = Shape's name = "I am a Shape" (reference type = Shape → static binding)
→ s.to_String() = Rectangle's version (actual object = Rectangle → dynamic dispatch)

Upcasting & downcasting

// Upcasting — always safe, implicit (subclass IS-A superclass) Shape s = new Rectangle(3.0, 2.0); // OK — Rectangle IS-A Shape // Downcasting — explicit, may throw ClassCastException at runtime Rectangle r = (Rectangle) s; // safe here because s really IS a Rectangle // Calling a subclass-only method on superclass ref → compile error without cast s.getArea(); // ❌ if getArea() is not in Shape ((Rectangle)s).getArea(); // ✅ cast first // Safe downcasting pattern if (s instanceof Rectangle) { Rectangle r2 = (Rectangle) s; // guaranteed safe }

Exam traps

🚫 Trap 1 — calling subclass-only method via superclass reference:
Shape s = new Rectangle(); s.display(); → compile error if display() is only defined in Rectangle. The compiler only knows s is of type Shape.
🚫 Trap 2 — ClassCastException at runtime:
Shape s = new Shape(); Rectangle r = (Rectangle) s; compiles fine but crashes at runtime. Always use instanceof before casting.
🚫 Trap 3 — field access is NEVER polymorphic:
Even if both parent and child have a field with the same name, field access always uses the declared reference type. This is the core of Q1 in the midterm.
💡 Quick test when tracing:
For every expression involving a reference variable, ask:
• Is it a field access? → Use the declared type of the variable.
• Is it a method call? → Use the actual runtime object type.

Interface — a pure contract

An interface defines a set of method signatures that any implementing class must provide. It cannot have constructors or instance state. It represents a can-do relationship (a Light can be controlled).

Interface syntax

public interface Controllable { // All methods are implicitly: public abstract public void turnOn(); public void turnOff(); public boolean isOn(); // Fields in interface are implicitly: public static final int MAX_DEVICES = 10; // really: public static final int MAX_DEVICES = 10; }

Midterm Q2 — the exact pattern you must know

// Step 1 — Interface defines the contract public interface Controllable { void turnOn(); void turnOff(); boolean isOn(); } // Step 2 — Abstract class PARTIALLY implements interface public abstract class SmartDevice implements Controllable { private String name; protected boolean on; // protected so subclasses can access directly public SmartDevice(String name, boolean on) { this.name = name; this.on = on; } public boolean isOn() { return on; } // ✅ implements isOn() public void turnOff() { on = false; } // ✅ implements turnOff() // turnOn() NOT here → subclasses must provide it public void displayStatus() { System.out.println("Name: " + name + " -- On: " + on); } } // Step 3 — Concrete class provides the remaining method public class Light extends SmartDevice { private int brightness; public Light(String name, boolean on, int b) { super(name, on); // calls SmartDevice constructor brightness = b; } public void turnOn() { // ✅ provides missing turnOn() on = true; brightness = 5; } public void displayStatus() { super.displayStatus(); // calls SmartDevice's version first System.out.println("Brightness: " + brightness); } }

Interface as a reference type

// Interface can be used as a reference type (polymorphism) Controllable c = new Light("Lamp", true, 7); c.turnOn(); // ✅ turnOn() is declared in Controllable c.isOn(); // ✅ isOn() is declared in Controllable c.getBrightness(); // ❌ compile error — not in Controllable interface! // Must cast to access subclass-specific methods ((Light) c).getBrightness(); // ✅ // Multiple interfaces public class SmartSpeaker implements Controllable, Playable { // Must implement ALL methods from BOTH interfaces }

Exam traps

🚫 Trap 1 — interface cannot be instantiated:
new Controllable() → compile error. You can only instantiate a concrete class, then store the object in an interface reference.
🚫 Trap 2 — abstract class doesn't finish implementing:
If an abstract class implements an interface but leaves some methods out, the first non-abstract subclass must implement ALL remaining methods — or it won't compile.
🚫 Trap 3 — overriding interface methods must be public:
Interface methods are implicitly public. If you try to implement one as protected or package-private in your class → compile error (you cannot reduce visibility).
💡 Exam pattern — UML to code:
Given a UML with a dashed arrow (interface) and solid arrow (extends):
1. Write the interface with its method signatures
2. Abstract class: public abstract class X implements Interface — implement what you can
3. Concrete subclass: extends AbstractClass — implement the remaining interface methods

Recursion — a method that calls itself

Solves a problem by breaking it into smaller subproblems of the same type. Must have a base case (stops it) and a recursive case (moves toward it).

General structure — always start here

static ReturnType method(type n) { if (/* base case condition */) { return /* direct value */; // ← STOP here, no recursive call } // recursive case: n must get CLOSER to base case return /* combine */ + method(/* smaller n */); }

6 common patterns — know all of them

Pattern 1 — Factorial (n! = n × (n−1) × … × 1)

static int factorial(int n) { if (n == 0) return 1; // base: 0! = 1 return n * factorial(n - 1); // n! = n × (n−1)! }

Pattern 2 — Sum of digits

static int sumDigits(int n) { if (n < 10) return n; // base: single digit, return it return n % 10 + sumDigits(n / 10); // last digit + sum of rest } // sumDigits(253) → 3 + sumDigits(25) → 3+5+sumDigits(2) → 3+5+2 = 10

Pattern 3 — Power (x^n)

static double power(double x, int n) { if (n == 0) return 1; // base: x^0 = 1 return x * power(x, n - 1); // x^n = x × x^(n−1) }

Pattern 4 — Count occurrences in array

static int count(int[] arr, int n, int val) { if (n == 0) return 0; // base: empty array, 0 occurrences return (arr[n-1] == val ? 1 : 0) + count(arr, n-1, val); // check last element, then count in remaining n-1 elements } // n is the number of elements to look at (start with arr.length)

Pattern 5 — Fibonacci (tree recursion — two calls)

static int fib(int n) { if (n <= 1) return n; // base: fib(0)=0, fib(1)=1 return fib(n - 1) + fib(n - 2); // TWO recursive calls → creates a TREE } // fib(4) = fib(3)+fib(2) = (fib(2)+fib(1))+(fib(1)+fib(0)) // = ((fib(1)+fib(0))+1)+(1+0) = ((1+0)+1)+(1+0) = 3

Pattern 6 — Print order (before vs after recursive call)

Print BEFORE → last-digit-first
static void printLast(int n) { if (n == 0) return; System.out.print(n % 10); // print printLast(n / 10); // recurse } // n=123 → prints: 3 2 1
Print AFTER → first-digit-first
static void printFirst(int n) { if (n == 0) return; printFirst(n / 10); // recurse System.out.print(n % 10); // print } // n=123 → prints: 1 2 3
Why? Print before recurse → current call does work first, then goes deeper (top-down). Print after recurse → goes all the way to base case first, then works back up (bottom-up). The stack unwinds, so printing happens in reverse order of the calls.

Tracing technique — the 3-step method

For any "what is the output/return value?" question:

  1. Unwind: Write each call, substituting the argument, until base case.
  2. Mark base case: This is the first concrete value you know.
  3. Fold back up: Substitute return values upward, computing each level.

Worked trace — factorial(4)

↓ Unwinding (calls build up on the call stack)
factorial(4) = 4 × factorial(3) = ?
factorial(3) = 3 × factorial(2) = ?
factorial(2) = 2 × factorial(1) = ?
factorial(1) = 1 × factorial(0) = ?
factorial(0) = 1   ← BASE CASE — first known value
↑ Folding back up (computing return values)
factorial(1) = 1 × 1 = 1
factorial(2) = 2 × 1 = 2
factorial(3) = 3 × 2 = 6
factorial(4) = 4 × 6 = 24  ← final answer

"Mystery function" — exam favourite

Given an unknown function, trace it and figure out what it computes:

static int mystery(int n) { if (n == 0) return 0; return mystery(n / 10) + n % 10; } // Trace mystery(253): // mystery(253) → mystery(25) + 3 // mystery(25) → mystery(2) + 5 // mystery(2) → mystery(0) + 2 // mystery(0) → 0 ← base // Fold: 0+2+5+3 = 10 → computes SUM OF DIGITS

Exam traps

🚫 Trap 1 — StackOverflowError:
If the base case is never reached (wrong condition, or recursive call doesn't shrink toward it), Java throws StackOverflowError. Always verify: does every recursive call make n smaller/simpler?
🚫 Trap 2 — off-by-one in base case:
if (n == 1) instead of if (n <= 1) will fail for n=0 or negative values. Always think: what is the very smallest/simplest valid input?
🚫 Trap 3 — tree recursion call count:
For functions with two recursive calls (Fibonacci), counting calls is exponential — do NOT count linearly. Draw the tree:
fib(4) generates: fib(3)+fib(2) = (fib(2)+fib(1))+(fib(1)+fib(0)) = 9 total calls.
🚫 Trap 4 — print before vs after:
The order of the print statement relative to the recursive call completely changes the output. Printing before = current value first. Printing after = deepest value first (reversed).
🚫 Trap 5 — missing return on recursive case:
return method(n-1); must have the return keyword. Forgetting it in a return-type method is a compile error. In a void method, no return needed — but the base case still needs to stop further calls.

Exception handling — graceful error management

An exception is a runtime event that disrupts normal program flow. Java's try-catch-finally lets you handle it gracefully rather than crashing.

Exception class hierarchy — know the tree

Throwable ├── Error ← JVM-level, do NOT catch │ ├── StackOverflowError ← infinite recursion │ └── OutOfMemoryError └── Exception ├── RuntimeException ← UNCHECKED (no compile requirement) │ ├── NullPointerException ← accessing null reference │ ├── ArrayIndexOutOfBoundsException │ ├── ArithmeticException ← e.g. division by zero │ ├── NumberFormatException ← bad Integer.parseInt() │ └── ClassCastException ← invalid downcast └── (direct Exception subclasses) ← CHECKED (compiler forces handling) ├── IOException └── FileNotFoundException ← subclass of IOException

Checked vs unchecked — the fundamental split

Checked exception
  • Extends Exception directly
  • Compiler forces you to handle it
  • Must use try-catch or declare throws
  • Examples: IOException, FileNotFoundException
  • Your custom exceptions (extend Exception)
Unchecked exception
  • Extends RuntimeException
  • Compiler does NOT require handling
  • try-catch is optional
  • Examples: NullPointerException, ArithmeticException
  • Usually represent programmer mistakes

try-catch-finally — full syntax

try { // Code that might throw an exception int result = 10 / 0; // ArithmeticException thrown HERE System.out.println("After error"); // ← NEVER REACHED if exception thrown above } catch (ArithmeticException e) { // catches only ArithmeticException System.out.println("Caught: " + e.getMessage()); } catch (Exception e) { // catches any remaining Exception System.out.println("General: " + e.getMessage()); } finally { // ALWAYS runs — no matter what System.out.println("Finally block"); }

throw vs throws — critical difference

throw

Used inside a method body. Actually throws an exception object right now.

throw new ArithmeticException("/ by zero"); throw new IllegalArgumentException("Bad input");
throws

Used in method signature. Declares that the method might throw that exception.

public void readFile(String name) throws IOException { ... }

Custom exceptions — exam pattern

// Step 1 — Create the exception class public class InsufficientFundsException extends Exception { public InsufficientFundsException(String message) { super(message); // passes message to Exception's constructor } } // Step 2 — Throw it (declare in method signature too) public void withdraw(double amount) throws InsufficientFundsException { if (amount > balance) { throw new InsufficientFundsException("Balance is only " + balance); } balance -= amount; } // Step 3 — Catch it try { account.withdraw(1000); } catch (InsufficientFundsException e) { System.out.println(e.getMessage()); // "Balance is only 500.0" }

Multiple catch — ORDER MATTERS

✅ Correct — specific first
try { ... } catch (FileNotFoundException e) { // child ... } catch (IOException e) { // parent ... }
❌ Wrong — compile error
try { ... } catch (IOException e) { // parent catches all ... } catch (FileNotFoundException e) { // unreachable! ... // ← COMPILE ERROR }
Rule: Always put the most specific (child) catch block first, and the most general (parent) last. Java tries catch blocks in order, and if a parent catches first, child blocks become unreachable — compile error.

finally — always runs

The finally block runs in ALL these cases:
✅ Exception thrown and caught
✅ Exception thrown and NOT caught (it runs before the exception propagates up)
✅ Return statement inside try block
✅ Return statement inside catch block
❌ Only skipped by: System.exit() or JVM crash

4 output tracing examples — practise these

Example 1 — basic try-catch-finally

System.out.println("A"); try { System.out.println("B"); int x = 10 / 0; // throws here System.out.println("C"); // skipped } catch (ArithmeticException e) { System.out.println("D"); } finally { System.out.println("E"); } System.out.println("F");
ABD ← exception caughtE ← finally runsF ← execution continues

Example 2 — exception NOT caught

try { System.out.println("A"); int[] arr = new int[3]; arr[5] = 10; // AIOOBE thrown System.out.println("B"); } catch (ArithmeticException e) { // wrong type! System.out.println("C"); } finally { System.out.println("D"); }
AD ← finally STILL runsthen exception propagates (crash)C is never printed

Example 3 — return inside try

static int test() { try { System.out.println("A"); return 1; // return scheduled } finally { System.out.println("B"); // runs before actual return } } // Calling: int x = test();
AB ← finally runs BEFORE returnx = 1

Example 4 — custom exception flow

try { System.out.println("A"); throw new InsufficientFundsException("Low"); System.out.println("B"); // unreachable } catch (InsufficientFundsException e) { System.out.println("C: " + e.getMessage()); } finally { System.out.println("D"); }
AC: LowD

Exam traps

🚫 Trap 1 — catch order:
Parent catch before child catch = compile error ("exception has already been caught"). Always order: most specific (child) first, most general (parent) last.
🚫 Trap 2 — finally runs even with return:
The finally block always executes, even if there's a return in the try or catch. The return is deferred until finally completes.
🚫 Trap 3 — wrong catch type = exception escapes:
If you catch ArithmeticException but the code throws ArrayIndexOutOfBoundsException, the catch block doesn't execute. The finally block still runs, then the exception propagates.
🚫 Trap 4 — custom exception must call super(message):
In a custom exception constructor, forgetting super(message) means e.getMessage() returns null. Always call super(message).
💡 Exam tracing formula for try-catch-finally:
1. Run try block line by line — stop at the first thrown exception.
2. Check catch blocks top-to-bottom — first matching type catches it.
3. If no catch matches, exception escapes (but finally still runs).
4. Finally block always runs before leaving the try-catch structure.
5. If exception was caught, execution continues after the entire try-catch-finally.

Files — reading and writing persistent data

Java uses streams to connect your program to files on disk. The two directions are: writing (output stream → file) and reading (file → input stream). All file operations are checked exceptions — you must handle IOException.

Writing to a file — the two patterns

Pattern A — PrintWriter (most common in exams)

import java.io.*; try { PrintWriter pw = new PrintWriter(new FileWriter("data.txt")); pw.println("First line"); // writes text + newline pw.print("No newline"); // writes text only pw.println(42); // can write numbers directly pw.close(); // MUST close — flushes buffer to disk } catch (IOException e) { System.out.println("Error: " + e.getMessage()); }

Pattern B — append mode (add to existing file, don't overwrite)

try { // Second argument 'true' = APPEND mode — existing content is kept PrintWriter pw = new PrintWriter(new FileWriter("data.txt", true)); pw.println("This is added to the end"); pw.close(); } catch (IOException e) { System.out.println("Error: " + e.getMessage()); } // Without 'true': new FileWriter("data.txt") OVERWRITES the entire file

Reading from a file — the two patterns

Pattern A — Scanner (easiest, most exam-friendly)

import java.io.*; import java.util.Scanner; try { Scanner sc = new Scanner(new File("data.txt")); while (sc.hasNextLine()) { // check if another line exists String line = sc.nextLine(); // read the whole line System.out.println(line); } sc.close(); } catch (FileNotFoundException e) { // Scanner throws FileNotFoundException System.out.println("File not found: " + e.getMessage()); }

Pattern B — BufferedReader (faster for large files)

try { BufferedReader br = new BufferedReader(new FileReader("data.txt")); String line; while ((line = br.readLine()) != null) { // readLine() returns null at end of file System.out.println(line); } br.close(); } catch (IOException e) { System.out.println("Error: " + e.getMessage()); }

Reading tokens (words/numbers) with Scanner

try { Scanner sc = new Scanner(new File("numbers.txt")); // If file contains: "10 20 30" int sum = 0; while (sc.hasNextInt()) { // check if next token is an integer sum += sc.nextInt(); // read the integer } System.out.println("Sum = " + sum); // Sum = 60 sc.close(); } catch (FileNotFoundException e) { ... }

Exception hierarchy for files

IOException ← parent — handles any I/O error └── FileNotFoundException ← child — file does not exist // FileWriter, BufferedWriter, FileReader, BufferedReader throw IOException // Scanner(File) throws FileNotFoundException (a subclass of IOException) // You can catch either: catch (FileNotFoundException e) { ... } // specific — file not found catch (IOException e) { ... } // general — any I/O problem

Try-with-resources — auto-close pattern

// Files declared in the try(...) are AUTOMATICALLY closed when the block ends // No need to call .close() manually — cleaner and safer try (PrintWriter pw = new PrintWriter(new FileWriter("out.txt"))) { pw.println("Auto-closed when done"); // pw.close() called automatically here, even if exception occurs } catch (IOException e) { System.out.println("Error: " + e.getMessage()); }

File class — checking before reading/writing

File f = new File("data.txt"); f.exists(); // true if file exists on disk f.getName(); // "data.txt" f.getPath(); // full path f.length(); // file size in bytes f.delete(); // deletes the file f.isDirectory(); // true if it's a folder // Common safe-read pattern: if (f.exists()) { Scanner sc = new Scanner(f); // read... }

Full read-and-process example — exam-style

// Read a file of student names and grades, compute average try { Scanner sc = new Scanner(new File("grades.txt")); int total = 0, count = 0; while (sc.hasNextLine()) { String name = sc.next(); // read first token on line int grade = sc.nextInt(); // read second token as int total += grade; count++; } sc.close(); System.out.println("Average: " + (double) total / count); } catch (FileNotFoundException e) { System.out.println("File not found"); }

Exam traps

🚫 Trap 1 — forgetting to close:
Not calling .close() means data may never be flushed from the buffer to disk. The file on disk could appear empty or incomplete. Always close, or use try-with-resources.
🚫 Trap 2 — overwrite vs append:
new FileWriter("file.txt") silently deletes all existing content and starts fresh. To preserve existing content, use new FileWriter("file.txt", true). This is a classic one-mark exam question.
🚫 Trap 3 — readLine() returns null, not empty string:
When BufferedReader reaches end of file, readLine() returns null — not "". The correct loop condition is while ((line = br.readLine()) != null), not while (!line.equals("")).
🚫 Trap 4 — mixing nextLine() with nextInt():
After sc.nextInt(), the newline character is left in the buffer. The next sc.nextLine() reads that leftover newline and returns an empty string. Fix: call an extra sc.nextLine() to consume the newline after each nextInt().
🚫 Trap 5 — Scanner(File) vs Scanner(System.in):
new Scanner(new File("data.txt")) → reads from a file (throws FileNotFoundException).
new Scanner(System.in) → reads from keyboard (no exception).
Mixing these up is a common mistake — always check what the Scanner is wrapping.
💡 Exam tip — which exception to catch:
If the question uses Scanner(File) → catch FileNotFoundException.
If it uses FileWriter, FileReader, BufferedReader → catch IOException.
Catching IOException always works (it's the parent), but being specific is better style and more likely what the exam expects.

Linked List — dynamic chain of nodes

A linked list is a sequence of Node objects where each node holds a value and a reference to the next node. Unlike arrays, size is dynamic and insertion/deletion does not require shifting elements.

Structure — two classes you always write

Node class
public class Node { private int data; private Node next; // reference to next node public Node(int data) { this.data = data; next = null; // new node points nowhere } public int getData() { return data; } public Node getNext() { return next; } public void setNext(Node n) { next = n; } }
LinkedList class
public class LinkedList { private Node head; // first node (or null if empty) private int size; // optional but useful public LinkedList() { head = null; size = 0; } public boolean isEmpty() { return head == null; } public int getSize() { return size; } }

Visualising the list — always draw this first

// head → [10|•]─→[20|•]─→[30|null] // ↑ ↑ ↑ // Node Node Node (tail — next is null) // data=10 data=20 data=30 // Empty list: head → null

Operation 1 — addFirst (insert at head)

public void addFirst(int data) { Node newNode = new Node(data); newNode.setNext(head); // ① new node points to OLD head head = newNode; // ② head now points to new node size++; }
Visual trace — addFirst(5) on list [10]→[20]→null
Before: head → [10|•]→[20|null]
① newNode.setNext(head): [5|•]→[10|•]→[20|null]  (new node linked in)
② head = newNode: head → [5|•]→[10|•]→[20|null]
🚫 ORDER MATTERS: You MUST do step ① (link new node to old head) BEFORE step ② (update head). If you do ② first, you lose the reference to the rest of the list forever.

Operation 2 — addLast (insert at tail)

public void addLast(int data) { Node newNode = new Node(data); if (head == null) { // empty list — new node becomes head head = newNode; size++; return; } Node current = head; while (current.getNext() != null) { // walk to the LAST node current = current.getNext(); } current.setNext(newNode); // last node now points to new node size++; }
Finding the last node: The loop stops when current.getNext() == null — that means current IS the last node. Then we set its next to the new node.

Operation 3 — display (traverse)

public void display() { Node current = head; // start at the head while (current != null) { // keep going until end of list System.out.print(current.getData() + " "); current = current.getNext(); // advance to next node } System.out.println(); } // NEVER do: head = head.getNext() — that would destroy the list! // ALWAYS use a separate 'current' pointer for traversal

Operation 4 — contains / search

public boolean contains(int val) { Node current = head; while (current != null) { if (current.getData() == val) return true; // found current = current.getNext(); } return false; // reached end without finding it }

Operation 5 — removeFirst

public void removeFirst() { if (head == null) return; // empty list — nothing to remove head = head.getNext(); // head skips over the first node size--; // old head is now unreferenced → garbage collected }

Operation 6 — remove by value

public void remove(int val) { if (head == null) return; // Special case: target is the head node if (head.getData() == val) { head = head.getNext(); size--; return; } // General case: walk list keeping track of the node BEFORE the target Node current = head; while (current.getNext() != null) { if (current.getNext().getData() == val) { current.setNext(current.getNext().getNext()); // ← bypass target node size--; return; } current = current.getNext(); } // If we reach here, val was not found }
Visual trace — remove(20) from [10]→[20]→[30]→null
Before: head → [10|•]→[20|•]→[30|null]
current = [10], current.getNext() = [20], getData() == 20 ✅
current.setNext(current.getNext().getNext()): head → [10|•]→[30|null] (node [20] bypassed)

Operation 7 — count / size by traversal

public int countNodes() { int count = 0; Node current = head; while (current != null) { count++; current = current.getNext(); } return count; }

Recursive operations on linked list

A linked list is naturally recursive: a list is either empty (null) or a node + the rest of the list. Exam questions often ask you to implement these recursively.

Count nodes recursively

public int countRec(Node node) { if (node == null) return 0; // base: empty list return 1 + countRec(node.getNext()); // 1 + count of rest } // Call: countRec(head)

Search recursively

public boolean searchRec(Node node, int val) { if (node == null) return false; // base: not found if (node.getData() == val) return true; // base: found it return searchRec(node.getNext(), val); // recurse on rest } // Call: searchRec(head, targetValue)

Display recursively

public void displayRec(Node node) { if (node == null) { System.out.println(); return; } // base System.out.print(node.getData() + " "); // print current displayRec(node.getNext()); // recurse on rest } // Call: displayRec(head) // To print in REVERSE — print AFTER the recursive call: public void displayReverse(Node node) { if (node == null) return; displayReverse(node.getNext()); // recurse first System.out.print(node.getData() + " "); // print after (reversed) }

Sum of all values recursively

public int sumRec(Node node) { if (node == null) return 0; // base: empty = 0 return node.getData() + sumRec(node.getNext()); } // Call: sumRec(head)

Generic linked list (if required)

public class Node<T> { private T data; private Node<T> next; public Node(T data) { this.data = data; next = null; } public T getData() { return data; } public Node<T> getNext() { return next; } public void setNext(Node<T> n) { next = n; } } // Usage: Node<String> n = new Node<>("Alice"); // Node<SmartDevice> n2 = new Node<>(new Light(...));

Exam traps

🚫 Trap 1 — wrong pointer order in addFirst:
Always newNode.setNext(head) before head = newNode. If you update head first, you lose the original list and cannot link the new node to it.
🚫 Trap 2 — advancing the head pointer during traversal:
Never write head = head.getNext() to traverse — you permanently destroy the list. Always use a separate current variable: Node current = head; then advance current.
🚫 Trap 3 — not handling the empty list:
Every method that touches head should check if (head == null) first. Operations like removeFirst(), addLast(), and display() all need this guard, otherwise you get a NullPointerException.
🚫 Trap 4 — remove needs TWO node references:
To remove a node from the middle, you need to find the node before it. The loop condition is current.getNext() != null (checking one ahead), not current != null.
🚫 Trap 5 — recursive linked list: parameter is Node, not int:
Recursive linked list methods take a Node parameter (the current node), not an index. The base case is always if (node == null). Call the method with head as the starting argument.
💡 Exam tip — drawing before coding:
For any linked list question, draw boxes and arrows FIRST. Label each node and each pointer (head, current, newNode). Then translate your drawing into code step by step. This eliminates almost all pointer-order mistakes.
✅ Pattern summary — three traversal templates:
1. Print/process all: while (current != null) { do work; current = current.getNext(); }
2. Find last node: while (current.getNext() != null) { current = current.getNext(); }
3. Find node before target: while (current.getNext() != null) { if (current.getNext().getData()==val) { ...fix pointers... } current = current.getNext(); }
